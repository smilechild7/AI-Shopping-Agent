# AX 개선 Phase 1 — 필수 조건 보존 및 검증

검증일: 2026-11-11 (KST). 로컬 구현과 자동 검증을 완료했다. 실제 OpenAI 호출, 배포, Phase 2 자동 재생성은 수행하지 않았다.

## 2026-11-23 실행 경로 연결 보충

위 검증일과 아래 Phase 1 본문은 과거 작업 기록이다. 11월 17~18일에는 관련 모듈이 실행 경로에 연결되지 않아 7개 테스트가 실패했으며, 11월 23일 사용자의 연결 지시에 따라 현재 런타임에 통합했다. 최신 검증은 **251/251 테스트 통과 및 production build 성공**이다. 과거의 205/205를 현재 집계로 사용하지 않는다.

현재 실행 순서는 다음과 같다.

```text
검색창의 메시지 + selectedFilters + previousResponseId
  → HTTP 입력 검증 + 연결 종료 AbortSignal
  → runtime의 응답 ID별 조건 저장소 조회
  → 사용자 문법·현재 UI 필터로 required 확정
    ├─ 모호함: 기존 responseId를 유지한 서버 clarification, 모델 호출 없음
    └─ 모델 호출: 모든 요청 instructions에 확정 required 제공
         → 검색 인자 정규화 + required 동일성 검사
         → SQLite 검색과 최신 후보 확보
         → 최종 JSON·후보 ID·evidence 검사
         → DB 재조회 + required 충족 검사
         → 마감 시각·취소 재확인 + 정상 responseId에만 스냅샷 저장
```

| 항목 | 현재 연결된 동작 |
|---|---|
| UI 필터 | 기존 합성 문장과 함께 선택적 `selectedFilters: { category, maxPrice, size }` 전송. 이번 선택값이 같은 필드의 문장 해석보다 우선한다. |
| 조건 보존 | 각 요청의 required는 불변이며 모델의 추가·누락·완화를 거부한다. 후속 명시 변경만 새 응답에 저장하며 부모 응답과 다른 분기는 유지한다. |
| 최종 상품 | 모델 evidence 유무와 별개로 DB의 실제 카테고리·가격·색상·사이즈를 확인한다. 필수 옵션 정보가 없으면 추천을 확정하지 않는다. |
| 자동 복구 | 검색 인자·조건·JSON·추천 검증 실패만 최대 1회. 인자 수정에는 수정된 검색과 최종 응답, 최종 응답 수정에는 추가 검색 없이 재검증을 요구한다. |
| 호출·시간 | 정상 모델 최대 3회, 복구 포함 최대 4회, 검색 최대 2회, 전체 요청 90초. 모든 SDK 호출의 내부 재시도는 0회다. |
| 취소 | HTTP 연결 종료 → 공통 예산 → SDK 신호로 전파한다. 취소를 무시한 어댑터의 늦은 반환과 마감 이후 DB 검증 결과도 저장하지 않는다. |
| 상태 만료 | 메모리에 최대 1,000개, 저장 후 30분 TTL. 만료·재시작·용량 초과로 사라진 이전 ID는 모델 호출 전에 HTTP 400 `invalid_conversation_state`로 거부한다. |
| 오류 응답 | 조건·출력 검증은 502 `agent_response_invalid`, 공통 timeout은 504 `agent_timeout`. DB·인증·네트워크 오류는 자동 재생성 대상이 아니다. |
| 관측 | 요청 ID, 최초·최종 결과, 복구 원인·시도·결과, 모델·검색 횟수, 복구 전후 토큰 사용량을 기록한다. 응답/사용량을 받지 못한 호출이 있으면 `usageComplete: false`다. |

`node scripts/runRecoveryEval.js`의 외부 API 없는 모의 재생에서 완료는 OFF 1/6 → ON 4/6, 조건 위반 결과는 양쪽 모두 0건이었다. 반복 오류 두 건은 복구 후에도 거부했다. 모델 호출은 12회 → 18회이며 실제 모델 품질·지연·비용 개선의 측정 결과는 아니다.

연결 자체에 사용자 수동 작업은 없다. 실제 OpenAI 평가·배포는 수행하지 않았다. 구현 파일과 검증 내역은 [상태 로그](IMPLEMENTATION_STATUS.md), 전체 HTTP·SQLite 경로의 자동 검증은 [runtime.integration.test.js](../server/runtime.integration.test.js)를 참고한다.

## 해결한 문제와 원인

사용자가 `5만원 이하 바지`를 요청해도 LLM이 재검색에서 `required.maxPrice`를 100,000원으로 바꾸면 90,000원 상품이 추천될 수 있었다. 기존 코드는 최근 tool 인자를 검색 기준으로 사용하고, 추천 근거도 그 기준과 대조했다. **사용자 조건과 모델이 만든 검색 조건을 구분하는 서버 기준값이 없었으므로, 검색과 응답 검증이 모두 통과해도 원래 요청을 위반할 수 있었다.**

기존 가격 보정은 단독 목표 가격(`8만원`)과 가격대(`8만원대`)를 보정했지만, 명시적 상한(`5만원 이하`)의 보존을 보장하지 않았다. 프롬프트에 조건 유지 지시가 있어도 실행 시 강제하지 못하는 문제였다.

## 구현 범위와 판단

```text
사용자 메시지 + 이번 요청의 UI 선택값
  → previousResponseId의 서버 스냅샷 조회
  → 지원 문법으로 명시적 변경만 반영
  → 요청 전체에서 불변인 required 확정
  → 모든 tool 호출의 required를 확정값과 비교
  → 기존 SQLite 검색 + soft retrieval
  → candidate/evidence 검증 + 최신 DB 필수 조건 재검증
  → 정상 응답 responseId에 새 스냅샷 저장
```

- `userConstraints.js`: 제한된 한국어 문법과 UI 입력으로 조건을 해석한다. LLM tool 인자는 사용자 의도로 취급하지 않는다.
- `requiredConstraints.js`: category/minPrice/maxPrice/colors/sizes를 정규화·동결하고, 조건 동일성과 상품 충족 여부를 분리해 검증한다.
- `constraintStore.js`: responseId별 불변 스냅샷을 메모리에 저장한다.
- `shoppingAgent.js`: 매 LLM 호출에 서버 기준을 제공하고, 검색 직전에 조건 변경·삭제·추가·hard→soft 이동을 차단한다. 같은 의미의 색상/사이즈 별칭과 배열 순서는 허용한다.
- `resultBuilder.js`: 기존 candidate/evidence 검증을 유지하면서 DB에서 다시 읽은 가격·category·색상·사이즈를 서버 기준과 대조한다. LLM이 가격 evidence를 생략해도 가격 검사를 한다.
- 클라이언트/API: UI 선택값을 문장에 합성하는 대신 선택적 `selectedFilters` 객체로 보낸다. 클라이언트가 보내는 조건 스냅샷은 받지 않는다. 기존 message/previousResponseId 요청도 지원한다.

조건 불일치를 조용히 덮어쓰거나 완화하지 않고 거부하도록 선택했다. 이 방식은 모델 오류를 관찰할 수 있으며, 이후 승인될 복구 기능에서도 원래 조건을 기준으로 재검증할 수 있다. 모델/프레임워크/의존성/DB schema는 변경하지 않았다.

### Hard / Soft 정책

category와 명시적 가격 조건은 hard로 유지한다. 일반적인 `흰색 원피스`의 색상과 `평소 66`의 체형 정보는 soft이며, LLM이 이를 hard로 추가하면 거부한다. `검정만`, 명시적인 판매 사이즈, UI 사이즈 선택처럼 필수임을 확인한 경우에만 hard로 반영한다.

기존 단독 목표 가격 정책도 유지한다. `8만원`은 ±10%를 만원 단위로 바깥쪽 반올림한 70,000~90,000원이고, `8만원대`는 80,000~89,999원이다. 이는 새로 추정한 제약이 아니라 기존 DEC-075/077 정책이다.

검색의 unknown-aware 색상/사이즈 필터는 유지했다. 값이 없는 상품은 검색 후보로 남을 수 있지만, **해당 속성이 사용자 필수 조건일 때는 최종 추천으로 확정하지 않는다.** 일반 soft 선호에는 이 최종 제한을 적용하지 않는다. 엄격한 조건에서는 추천 수나 완료율이 줄 수 있는 의도적인 선택이다. 색상/사이즈의 상품 매칭에는 기존 별칭·범위 겹침 규칙을 사용하며, 조건 스냅샷끼리 비교할 때는 정확한 동일성을 사용한다.

## 서버가 해석하는 문장 범위

범용 한국어 이해기가 아닌 제한된 문법이다. 아래 문법과 기존 자연스러움 평가 20개 입력을 로컬에서 검사했다.

| 항목 | 지원 예 | 동작 |
|---|---|---|
| category | 바지/팬츠/슬랙스/청바지, 상의/윗도리/블라우스/셔츠/티셔츠/니트, 원피스/드레스, 치마/스커트, 아우터/재킷/자켓/코트/가디건 | 단일 검색 대상 category 확정. `청바지랑 입을 니트`의 동반 의류는 제외 |
| 금액 | 숫자 + 원/만원/천원, `30,000원`, `1천원`, `천원` | 음수가 아닌 정수 원으로 정규화 |
| 상한/하한 | `5만원 이하/이내/까지/아래`, `3만원 이상/부터`, `최대 가격을 10만원으로 변경`, `최소 가격은 3만원` | 해당 경계만 변경, 언급하지 않은 경계는 유지 |
| 배타적 경계 | `5만원 미만`, `3만원 초과` | 각각 49,999원 이하, 30,001원 이상 |
| 범위/정확한 가격 | `5~7만원`, `50,000원~70,000원`, `딱 5만원` | min/max를 함께 확정 |
| 목표 가격/가격대 | `8만원`, `8만원 정도/쯤/전후`, `8만원대` | 기존 근사 범위/가격대 정책 적용 |
| 필수 색상 | `검정만`, `꼭 정확한 화이트`, `검정 또는 네이비만` | 명시된 색상 또는 허용 목록만 hard. 일반 색상 선호는 soft |
| 기존 필수 색상 변경 | `네이비로 바꿔줘`, `아이보리도 괜찮아` | 기존 필수 색상이 있을 때 교체/허용 목록 추가 |
| 판매 사이즈 | `판매 사이즈 M`, `사이즈=M`, `M 사이즈만`, `28 사이즈가 있는 바지` | 판매 옵션만 hard. 평소 체형 사이즈를 판매 옵션에 대응하지 않음 |
| 조건 해제 | `가격 제한을 없애줘`, `색상은 상관없어`, `사이즈는 상관없어` | 지정한 조건만 해제 |
| 변경 없는 후속 요청 | `후기가 더 좋은 걸로` | 기존 필수 조건 전체 유지, soft 선호는 모델이 조정 가능 |

색상 어휘는 black/white/navy/blue/gray/charcoal/beige/brown/khaki/cream 계열의 코드에 명시된 한·영 표현으로 제한한다. 아이보리/크림은 기존 동일 계열 매핑을 유지하고, white와는 구분한다. 사이즈는 XS/S/M/L/XL/XXL/FREE 또는 2~3자리 숫자·숫자 범위다. 재고나 체형 적합성까지 보장하는 값은 아니다.

다음과 같은 입력은 조건을 임의 변경하지 않고 서버 clarification을 반환한다.

- 상대 변경: `예산을 조금 늘려줘`, `사이즈를 더 큰 걸로 변경`.
- 충돌/부정/인용/조건문: `5만원 이하 또는 10만원 이하`, `10만원으로 올리지는 마`, 인용된 조건, `10만원 이하라면`.
- 변경과 범위가 혼합된 표현: `5만원에서 10만원으로 올려줘`. `최대 가격을 10만원으로 변경`처럼 다시 명시해야 한다.
- 미지원 금액/엄격 색상: `십만원 이하`, `5만 5천원 이하`, `1억원 이하`, `보라색만`.
- 상품 가격 언급과 예산 변경이 구분되지 않는 표현: `아까 추천한 9만원 상품의 후기는?`, `9만원짜리 상품이 좋아 보여`, `10만원보다 비싸면 안돼`.
- 기존 필수 색상과 다른 색상을 모호하게 언급: `네이비도 보여줘`.

모호함을 감지하면 **요청 전체를 반영하지 않는다.** 기존 스냅샷과 responseId를 유지하고 LLM/search를 호출하지 않는다. 최초 요청이면 responseId는 null이다. 이 clarification에는 새 대화 상태나 미확정 조건을 저장하지 않으므로 다음 입력에서 원하는 조건을 완전하게 다시 명시해야 한다. 단순 `네`, `그렇게 해줘`로 앞선 완화 제안을 자동 승인하는 기능은 없다.

이번 요청의 UI 선택 category/maxPrice/size는 같은 필드의 자연어보다 우선한다. 가격 상한 UI를 선택하면 기존 하한도 지워 UI 선택의 의미를 유지한다. 다음 요청에서 명시한 자연어 변경은 이전 UI 값보다 우선한다. UI 필드를 생략하는 것은 기존 조건을 해제한다는 의미가 아니다.

모든 미지원 자연어를 완벽하게 탐지한다는 보장은 없다. 새 문법을 추가할 때는 먼저 조건 오해 사례를 테스트로 고정해야 한다. 특히 복잡한 다중 문장·부정·과거 상품 설명·문맥 의존 응답에는 명확한 재입력을 우선한다.

## responseId 상태와 오류 처리

| 항목 | 구현/한계 |
|---|---|
| 저장 구조 | Agent 인스턴스의 Map, responseId → 동결된 required + expiresAt. 사용자 원문 저장 없음 |
| 저장 시점 | 유효한 모델 recommendation/no_result/clarification을 처리한 뒤 저장. 오류 요청과 서버 ambiguity clarification은 새 상태를 저장하지 않음 |
| 만료 | 저장 후 30분 고정 TTL. 읽기로 연장하지 않음. get/set 때 만료 항목 제거 |
| 최대 크기 | 1,000개. 초과 시 가장 먼저 저장한 항목 제거. 따라서 30분보다 일찍 제거될 수도 있음 |
| 분기 | 동일 부모 responseId에서 파생된 응답은 각각 새 스냅샷. 부모/다른 분기를 덮어쓰지 않음 |
| 실패 요청 | 이전 유효 스냅샷을 유지. 실패한 요청의 조건 변경은 commit하지 않으므로 다시 변경하려면 원래 요청 재제출 |
| 만료·재시작·배포 | 상태가 없으면 LLM 호출 전 HTTP 400 `invalid_conversation_state`. 조건을 추측하지 않고 `새로 찾기`로 다시 시작 |
| 다중 인스턴스 | 메모리 공유가 없어 지원하지 않음. 현재 단일 인스턴스의 최소 구조이며 DB/Redis/persistence는 도입하지 않음 |
| 모델 조건 위반/DB 불일치 | HTTP 502 `agent_constraints_invalid`. 일반 `agent_response_invalid`와 구분하여 사용자에게 조건 완화를 요구하는 기존 UI recovery로 바꾸지 않음 |

구조화 로그에는 requestId, 오류 code와 field, 응답 유형, 호출 수, 기존 usage 합계를 남긴다. 실제 사용자 원문이나 조건값은 새 검증 로그에 기록하지 않는다. 기존 SDK의 일시적 네트워크 오류 재시도와 기존 soft 재검색 정책은 유지하지만, **검증 실패 후 자동 재생성은 추가하지 않았다.**

## 사실 검증의 범위

세 종류를 구분해서 설명해야 한다.

1. **DB 사실 필드:** 이름·가격·URL·색상·판매 사이즈 등은 서버가 DB에서 합성한다. 이번 단계에서 사용자 필수 조건 충족 여부를 추가로 검증했다. DB 자체의 수집 정확도와 최신성까지 보증하는 것은 아니다.
2. **구조화된 근거:** candidate ID, evidence enum/value, 후기 신호와 tag는 기존 검증을 유지한다. enrichment된 후기 신호/tag는 원문에서 유도된 정보이며 독립적으로 확인된 객관적 사실과 구분한다.
3. **검증되지 않은 설명:** message/reason/strengths/concerns/comparison 등 자유 서술 전체의 사실성은 증명하지 않는다. 예를 들어 본문에 잘못된 가격을 서술하는 모든 경우를 탐지하지는 못한다. Phase 1에서 UI를 재설계하거나 자연어 전체 검증기를 도입하지 않았다.

## PT에 사용할 성과와 남은 범위

> 재검색 중 모델이 예산을 임의로 올려도 기존 검증을 통과하는 문제를 재현했습니다. 원인은 사용자 요구와 모델의 검색 인자를 같은 기준으로 취급한 것이었습니다. 서버가 사용자 조건을 별도로 보존하고 검색 전·DB 조회 후 두 번 검증하도록 바꿨습니다. 같은 결함 테스트에서 9만원 상품의 잘못된 추천이 차단됐고, 사용자가 직접 예산을 변경한 경우는 정상 동작함을 검증했습니다. 기존 테스트를 포함한 205개 테스트와 빌드를 통과했습니다.

기업 AX와의 연결점은 **LLM이 제안하는 실행 인자와 기업이 확정한 업무 규칙을 분리하는 것**이다. 예산·구매 정책·승인 범위처럼 변경 권한이 중요한 규칙을 서버에서 보존하고, 자동화의 실행 전과 최종 결과 확정 전에 검증하는 패턴으로 설명할 수 있다. 실제 기업 시스템에 적용하거나 효과를 측정한 결과는 아니다.

남은 검증은 실제 모델의 정상 완료율, 오류 차단율, 응답시간 p50/p95, 토큰 및 비용의 동일 조건 비교다. 이번 단계의 실제 외부 API 호출은 0회이며, mock 실행 시간/usage를 실서비스 성능·비용 지표로 사용하지 않는다. 상태 만료·엄격 조건의 unknown 처리·보수적 문법으로 생기는 clarification/거부 증가도 함께 측정해야 한다.

Phase 2는 별도 승인 후에만 시작한다. 복구 가능한 오류에 한한 최대 1회 재생성 및 재검증, 실제 API 기반 전후 비교는 이번 완료 범위에 포함하지 않는다. 사용자 수동 작업은 없다. 기존 모바일 UI 수동 확인 과제는 별도로 남아 있다.
